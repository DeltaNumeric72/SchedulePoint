## 1. Design decisions required by findings (FD-5..FD-9)

### FD-5 (V-13) — Where a picklist selection lands
**Decision:** accepted selections produce **picklist-owned daily-assignment records**, not schedule-version snapshots. New table `daily_assignments` (org/group-scoped, RLS'd; `picklist_id`, `selection_id` unique, `membership_id`, `work_item_id`, `assignment_date`, provenance) written in SPEC-02 §3 step 13; `selections.resulting_assignment_id` → **`resulting_daily_assignment_id`**. The daily sheet renders published-version assignments **plus** the daily-assignment overlay; published schedule versions are never touched by a live turn, so D-15a and I-16 no longer interact at all. SPEC-05 §9's "picklist corrections produce a new version" is corrected: picklist corrections revise **daily assignments** (audited), not schedule versions. **Rationale:** matches the source's own concept split (master schedule vs. daily assignment sheet — Confirmed); removes the trigger/turn-transaction collision the reviewer found; keeps the turn transaction single-aggregate. **Parity:** high (mirrors observed model). **Reversibility:** R2. **Verification:** P-series gains a case asserting a selection never writes any `assignment_snapshots` row; V-series unaffected.

### FD-6 (V-16) — `external_reference` pseudonymization
**Decision:** the enclave never emits a source-assigned reference. It emits **`external_ref_pseudonym` = HMAC-SHA256(connector-scoped secret, source reference)**, computed inside the enclave with a key held in the enclave's own secret scope (separate trust domain, TDG-13), never available to the application role. Same source record → same pseudonym → reconciliation and replay still work; the raw reference never crosses the boundary. Key rotation uses a dual-pseudonym overlap window. Quarantine rules unchanged (no values, no hashes of **rejected** content). §7.1 canaries **must include MRN-shaped and health-card-shaped values** in every sweep. **Rationale:** the review's unkeyed-hash objection was about publicly-enumerable inputs; a keyed MAC with an enclave-held key is standard pseudonymization and the only option that preserves reconciliation (a platform-minted token with no stored correlation breaks update matching; declaring residual risk was the do-nothing option). **Residual risk stated:** key compromise re-identifies references — mitigated by trust-domain isolation and rotation; recorded in risk register. **Reversibility:** R2.

### FD-7 (V-15) — Enclave vocabulary distribution
**Decision:** the enclave validates vocabulary membership against a **signed, versioned vocabulary snapshot** pushed/pulled over its existing platform-ingress-API channel (E-9 already allows it), refreshed on interval and on vocabulary-change notification; **a stale-snapshot miss quarantines, never accepts**; no candidate value is ever transmitted for resolution; the application-side ingestion module **re-validates resolution authoritatively at write time** (defence in depth — a snapshot race cannot admit an unresolved ref). E-10 (no DB credential) stands. **Reversibility:** R1.

### FD-8 (V-21) — D-1b enforcement mechanism
**Decision:** D-1b is enforced on a **real table**: `current_published_assignments` (org/group/membership, time range, source version/snapshot refs; RLS-enabled), maintained **inside the publication transaction** (delete outgoing version's rows, insert incoming version's rows, under the period-scoped serialization publication already holds) — with the **`EXCLUDE`** constraint declared on that table. Cross-period double-booking then fails the *publishing* transaction, which is the correct place. Locking: contention is per-membership rows, not a global lock; V-15 (SPEC-05 test) is now executable. The materialised-view text is withdrawn. **Reversibility:** R2.

### FD-9 (V-27) — Vacation as a true subtype
**Decision:** `vacation-selection` **is** a subtype under D-18/19/20: §1.2 gains its row (required: `vacation_period_id`, week references; prohibited: `shift_type_id` etc.); §2 gains its column; **`requests.status` for vacation is derived — synchronized in the same transaction — from `vacation_selections.status`** via a stated mapping (`pending→submitted`, `approved→approved`, `committed→reflected_in_version`, `denied→denied`, `withdrawn→withdrawn`, `expired→expired`, `reversed→reversed`†). †`reversed` is added to the root status domain for the vacation column only (D-20 per-subtype domains make this legal). One writer rule: only the vacation module updates either status, always both, same transaction. **Reversibility:** R2.
