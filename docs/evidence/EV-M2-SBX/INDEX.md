## SBX-002 — which layer answered, stated because the count alone would mislead

**12 of the 15 SPEC-06 rows execute**, in **15 concrete cases** (some rows carry
more than one — L1.2 has both revoked and suspended, L3.2 has ended, suspended
and invited). The remaining three rows have no surface and are `EVIDENCE_BLOCKED`.
Each denial is preceded by an **ALLOW control on the same actor and route**, so it
cannot count when the actor was never allowed.

The cases do not all get refused in the same place, and the evidence says so.
**These numbers are read from
[`sbx-002-truth-table.txt`](sbx-002-truth-table.txt), not typed by hand** — an
earlier version of this table said 9/6 while the artifact said 8/7, which is
exactly the drift that comes of maintaining a summary separately from its source:

| Cases | Refused by |
|---|---|
| **8 of 15** | the **SPEC-06 evaluator**, reporting its own layer |
| **7 of 15** | **SPEC-01 §2.3 context resolution, before the evaluator runs** |

That split is the architecture as specified, not a gap. An inactive organization
or group, and a membership that is absent, ended, suspended, invited or out of
window, are all resolved when the context is resolved — and both layers answer
the same **404**, so nothing leaks either way.
`http-authorization.test.ts` already records the same division with its
`deniedBy: 'context'` cases.

**What this scenario claims:** every row has a concrete server-side case.
**What it does not claim:** that every row is demonstrated *at the evaluator
layer*. The exhaustive evaluator-level evidence is
`packages/domain/test/authz/cross-product.test.ts` — **39,285,000 cases against
an independent oracle, 0 disagreements** — cited in the scenario's
objective-oracle field with the sampling relationship stated. Neither substitutes
for the other: an exhaustive evaluator wired to nothing would still pass its own
test.

## SBX-001 — three outcome classes, not two

The matrix classifies every `(role, route)` cell as one of **three** defined
outcomes, and that third class was found by running it rather than by design:

| Class | Statuses | Meaning |
|---|---|---|
| explicit allow | 2xx | authorized |
| clean deny | 403 / 404 | the authorization layer refused |
| **context refusal** | **409** | SPEC-01 §7.1's `CONTEXT_STALE` / `CONTEXT_TARGET_MISMATCH` — a server-authoritative "re-fetch and retry" |

The first version accepted only allow and deny, and a cross-group target
legitimately answered **409**. Filing a precondition failure under "authorization
denial" would have misdescribed what the server did, so the three classes are
counted and reported separately. A matrix that is executed finds this; a matrix
that is described does not.

## The controls, and the red cases that prove them

The harness's own controls are only worth something if they have been seen to
fail. Five red cases, all in `apps/api/test/sbx/sbx.test.ts`:

| Red case | Proves |
|---|---|
| a contract field blanked | the scenario is **NOT_RUNNABLE** and the validator names the field (SPEC-16 §1) |
| a probe that cannot fail | the scenario is **VACUOUS**, not PASS, and the run fails |
| a fully blocked scenario | **EVIDENCE_BLOCKED** with its dependency named — never a pass, never a silent skip (SPEC-16 §7) |
| a blocked sub-scenario with a blank dependency | **NOT_RUNNABLE** (SPEC-16 §6: named, not absorbed) |
| the SAME blocked scenario, **gate-required** vs not | blocked **fails the run** when a gate claims the evidence, and is tolerated when none does — a gate whose evidence cannot be produced is a gate that has not been met |
| a probe throwing a **TypeError** | **PROBE_ERROR**, not FALSIFIABLE — the run fails |
| a probe throwing a **SQL error** | **PROBE_ERROR**, not FALSIFIABLE — the run fails |
| a scenario declaring a **phantom artifact** | the SPEC-16 §7 meta-test fails the run |

### Why the probe rule is a typed sentinel

The first vacuity detector recorded FALSIFIABLE on **any** throw. The independent
review broke it three ways — a `TypeError`, a SQL syntax error, and a sweep that
never executed — each of which was laundered into a green control. It was
measuring "did an exception occur", which is not the question.

A probe must now **observe the scenario's own oracle reject** and then throw the
typed `ProbeFalsified` sentinel. Any other throw is `PROBE_ERROR` and fails the
run, because a probe that crashed proved nothing and must not be mistaken for one
that worked.
| **FORCE RLS removed** on `memberships` | the SBX-004 sweep sees **15 foreign rows** and would fail — so it is measuring RLS, not describing it |

The RLS red case never leaves the cluster weakened: the DDL and the probe share
one connection inside one transaction, PostgreSQL DDL is transactional, and the
test verifies `relforcerowsecurity` came back **from a fresh connection** rather
than assuming the `ROLLBACK`.

## The phase-A honesty note, closed — and the 12-vs-13 census reconciled

Phase A said **12**; SBX-004 says **13**. Both are right about different sets, and
the difference is exactly one table: **`users`**.

`TENANT_TABLES` (`apps/api/src/db/schema.ts`) has **13** entries. Twelve carry a
tenant column and are swept by the same predicate. The thirteenth, `users`, is
**global by PO-DEC-06** and reachable only *through* a membership — it has no
`organization_id` to compare — so the phase-A prototype **excluded it from the
sweep** and reported over the remaining 12. Excluding it was right for that
predicate and wrong as a coverage claim: `users` is a tenant-visible table and
leaving it out of the count made the sweep look narrower than it needed to be
about a table it simply had not probed.

SBX-004 sweeps the 12 with the tenant-column predicate **and** probes `users` on
its own terms — a Beta-only user must be invisible under an Alpha context
(`users_readable_through_membership`) — so it accounts for **13 of 13**.

| Census | Count | Which |
|---|---|---|
| `TENANT_TABLES` | **13** | the registry |
| swept by tenant-column predicate | 12 | everything except `users` |
| probed through membership | 1 | `users` |
| **SBX-004 total** | **13** | all of them |

**The vacuity half.** The NR-13 prototype probed **3 of its 12** vacuously —
`capability_grants`, `audit_checkpoints` and `outbox_effects` had no visible rows
under its organization-scoped `app_runtime` context, so "0 wrong" there meant
nothing. SBX-004 closes that too: it sweeps under **`app_runtime` and
`app_worker`**, in **organization and group** contexts, on **both sides** of the
organization boundary, and asserts every table was observed with visible rows.
`audit_checkpoints` and `outbox_effects` are `app_worker`'s alone (migration
0003's grants, SPEC-11 §2) — using that role is what makes their probes
non-vacuous.

## The three arms of SBX-004

| Arm | What it proves | Coverage |
|---|---|---|
| **role-scoped SQL read** | RLS refuses a foreign ROW | **all 5 application roles** × 13 tables |
| **cross-tenant WRITE** | no role can write across the boundary | 3 RLS-bound roles × 4 tables × UPDATE/DELETE = 24 attempts, all in rolled-back transactions, **0 landed** |
| **API surface** | the HTTP layer refuses a foreign IDENTIFIER byte-identically to a non-existent one | the tables with a registered route today |

Tables with no route yet are **named in the scenario report** as SQL-arm-only,
not silently omitted.

### Two declared cross-tenant paths — pinned, not omitted

"No second cross-tenant path exists" is only a complete claim when every known
path is named in the same evidence. Both are asserted positively here, and the
sweep fails if either disappears:

| Path | Status |
|---|---|
| **`app_breakglass`** BYPASSRLS (SPEC-01 §4.4, pinned by A-08) | asserted: holds BYPASSRLS and sees ≥2 organizations with no context |
| **`app_migrator`** → `audit_checkpoints` (FAD-14 maintenance plane, SELECT-only) | asserted: must read foreign checkpoint rows, or the exception is stale |

The FAD-14 path is excluded from the leak check by the **exact (role, table)
pair** — never a role-wide or table-wide waiver, because a wider waiver would let
a genuine second path hide behind the sanctioned one. It was **found by extending
the sweep to all five roles**, which the earlier two-role sweep could not have
seen.

**Refused reads are recorded distinctly.** Some roles hold no EXECUTE on helper
functions an RLS policy calls, so a read raises 42501 rather than returning zero
rows. That is stronger isolation than "saw nothing", and folding it into
`visible = 0` would hide which mechanism did the work.

## The audit chain after the run

Every run verifies the chain per organization and records the shape
**chain problems / checkpoints signed / checkpoint problems**; clean is `0 / N≥1 / 0`.
The middle number is reported rather than pinned, because the periodic sweep may
legitimately have signed more than one and pinning it would make an unrelated
change look like a chain failure. The current values are in
[`scenario-report.txt`](scenario-report.txt).

## Running it

```bash
corepack pnpm sbx                 # runs the subset and prints the scenario table
```

The scenarios live in `apps/api/test/sbx/` and execute inside the api test
project, so they are also covered by `corepack pnpm check`. They need the real
migrations, the real five roles, the real MULTI fixture and the real server; a
standalone harness with its own cluster would be a second copy of all of that.
