WHAT THIS ESTABLISHES — and it is what REV-B said it could not establish by construction:

 1. THE STRAGGLER IS THE PAGE'S OWN QUERY, NOT THE CLICK. On run 5 the captured request is
    literally printed:
capturedInWindow=["http://127.0.0.1:41988/api/organizations/11111111-1111-4111-8111-111111111111/groups/22222222-2222-4222-8222-222222222222/schedule/periods"]
    — a GET on the periods LIST endpoint, issued at +182 ms, 6 ms AFTER the window opened at
    +176 ms. The click issues nothing. REV-B-001's product-innocence half is now proven from
    the failing side as well as the passing side.

 2. THE SAFETY MARGIN IS SINGLE-DIGIT MILLISECONDS, ON EVERY RUN. This is not a rare
    coincidence of scheduling; it is a systematically near-simultaneous pair whose ordering is
    decided by noise. An I-13/I-10 invariant proof currently rests on a ~8 ms gap. Any change
    that shifts either side by ten milliseconds — a slower runner, a different Chromium build,
    one more mocked route — flips the outcome. That is why re-running until green is not a
    repair, and why REV-C grades REV-C-001 BLOCKING rather than treating it as flakiness.

 3. THERE ARE TWO PERIODS REQUESTS PER LOAD, AND THE SECOND IS THE PROBLEM. REV-C did not
    prove what causes the second one and does not claim to. It is recorded as an OBSERVATION
    for the repair packet, with the note that its shape — a second fetch of the same key ~150
    ms after the first, once another query has settled — matches the enabled-oscillation class
    GH-006 diagnosed on the publication comparison page and GH-009 registered as still open
    ('the enabled-oscillation class has one confirmed latent sibling'). Whether this is a
    third instance of that class is a question for the implementer, not a REV-C finding.

BIAS DISCLOSED: REV-C's composed run #2R was executing throughout, so this machine was loaded.

capacity, and the same shape appears on all 22 runs including the fastest.
