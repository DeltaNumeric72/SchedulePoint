### 2.1 Two places the harness states the claim more precisely than the table does

Both are recorded rather than resolved silently.

1. **Byte-identity is split in two.** V-02 says "sha256 of every V1 row". Read literally
   that includes V1's own `schedule_versions` row — which V-08 then *legitimately*
   changes, because publishing V2 sets V1's `is_current`, `state`, `superseded_at` and
   `superseded_by_version_id` through D-15b's permitted transitions. A proof demanding
   that row be frozen would contradict §4.1. The harness therefore proves **content
   byte-identity** (child rows + rendered report + feed, frozen absolutely) *and*
   **version-row discipline** (only the permitted columns moved, observed empirically)
   separately. One number for both would have hidden which held.

2. **V-12 is proven in two arms.** SPEC-05 §6's note describes the mechanism for two
   publications of the *same* version — the loser fails at step 03. V-12 is written as
   "publish V2 and V3 concurrently", i.e. *different* versions, which would both
   legitimately succeed in sequence. Arm (a) races the same version; arm (b) supplies the
   caller's expected-current view (`expectedPriorCurrentVersionId`, optional and absent
   from §6's signature) so the second is a stale decision and is refused explicitly. Both
   arms assert the binding invariants.

## 3. SBX-018 — PASS with falsifiability

Declared with **all nine SPEC-16 §1 contract fields** in
`apps/api/test/sbx/scenario-018.ts`. Retained artifact: `sbx-018.txt` (this directory).

| Pass criterion (report 18 §5.3) | How it is counted |
|---|---|
| no version is ever destroyed | the version-id set before the revision is a subset of the set after, and every id still resolves; the revert publishes **forward** as n=3 |
| concurrent publication is serialised | two simultaneous publications of one period → exactly 1 fulfilled, 1 rejected, exactly 1 current version. Asserted on the outcome **set**, never on which won, so it cannot depend on interleaving |
| affected staff are notified, others are not | affected == notified **exactly**. A reassignment affects **both** the losing and the gaining membership; the untouched third membership is asserted **not** notified |

**The probe** attacks the realistic failure — a diff that gives up and notifies everyone,
which any subset-only check would accept. It first confirms the oracle accepts the
*correct* set (so a broken oracle is reported as an error, not as falsification), then
feeds it a set containing a provably unaffected membership and throws `ProbeFalsified`
only after **observing** the rejection.

Battery result: `SBX-001 / 002 / 004 / 005 / 006 / 018` — **6 PASS, all
`probe=FALSIFIABLE`**, 0 vacuous, 0 probe-error, 17 tests.

## 4. I-11 — proven from both sides

`apps/api/test/schedule/publication-invariants.test.ts`.

| Half | Instrument | Result |
|---|---|---|
| **A — pre-commit** | the outbox write (inside the transaction) is made to throw | the publication rolls back **whole**: version back to `approved`, `version_number` NULL, **0** reality rows, **0** publication records, **0** supersessions |
| **B — post-commit** | `AlwaysFailingSink` (the repository's existing I-11 instrument) fails delivery of a **committed** publication | delivery is genuinely attempted and genuinely fails; the version stays `published`, `is_current`, numbered, with its reality rows and publication record intact |

Half A is injected through a narrow `publishOutbox` seam that substitutes one row-writing
function for one that throws. It widens no permission, skips no check, and no production
caller passes it. Without it the pre-commit half is unprovable, and an unprovable
invariant is what this repository treats as a defect.

**No delivery is attempted to any destination in any test.** Notifications are outbox
intents only; payload bodies are never logged.

## 7. What running found, and what it cost

Nine defects were found **by running**, not by reading. They are listed because the
list is the evidence that the suite can fail.

1. Audit/outbox payload keys must match `/^[a-z][a-zA-Z0-9]{0,39}$/` — **no underscores**.
   Every schedule payload key is now camelCase.
2. The D-15a child guards ran as `app_runtime` and could not execute the `REVOKE`d
   `SECURITY DEFINER` helper. Fixed by making the guards `SECURITY DEFINER` (the 0007
   idiom) rather than granting app roles `EXECUTE` on the helper — a grant would have
   opened a cross-tenant existence oracle to spare a keyword.
3. The sibling-group seed used a membership without the `schedule.publish` grant and was
   denied at L4.2 — **the control working**, since publish is grant-only.
4. `node-pg` parses `date` (OID 1082) as a `Date` at **local** midnight; `toISOString()`
   west of UTC renders the previous day, which would have made the renderer
   machine-dependent and quietly destroyed the byte-identity proof.
5. V-07 as first written proved the **grant**, not D-15c: `app_runtime` holds no `DELETE`
   at all, so it never reached the trigger.
6. **R-05 violated** — `GRANT DELETE on current_published_assignments` broke the standing
   invariant that no runtime role holds `DELETE` on any tenant table (doc 09 §4). Replaced
   by `app_schedule_prune_current_assignments`: `SECURITY DEFINER`, one source version,
   tenant read from transaction-local context, fail-closed without one.
7. **X-11 violated** — D-16's partial unique index was on `(period_id)` alone and so was
   not tenant-qualified. Now `(organization_id, group_id, period_id)`, which costs D-16
   nothing because `period_id` already determines both tenant columns.
8. `revokeGrantsById` **flips `granted` to false in place** rather than deleting or closing
   a window, producing an EXPLICIT DENY that leaked into a later test in the same file.
9. **The V-harness was order-dependent** — see below.

### 7.1 The fixture-regression finding

`corepack pnpm fixture-regression` failed on **all fourteen seeds**, not one. The cause was
structural, not flake: V-01..V-11 are a **sequence by construction** (V-02 hashes what V-01
published; V-04 re-hashes after V-03's clone; V-08 after a second publication; V-11 after a
third), and they were expressed as eleven independent `it()`s that vitest's test-order
shuffle was free to reorder.

Splitting them was the defect; the per-row **reporting** was never the problem. The chain is
now one test that runs each row as a named step — every row still asserted separately, every
row still recording its own verdict, the printed proof table unchanged, and a break still
names the row that broke. Two further order dependencies surfaced in the same investigation
and were fixed rather than papered over: the matrix rows borrowed the chain's `v3` as a
supersede target (so they needed the chain to have run), and they left orphaned reality rows
behind that a global invariant then reported.

## 7b. The revision round — FAD-22 (independent review findings)

The first submission was **REVISE**. Two blocking defects, both real, both found by
reviewer-authored probes rather than by reading. SPEC-05 §4 was amended (**FAD-22**) and
the branch rebased onto that amendment.

### B-1 — the prune was a general delete primitive

`app_schedule_prune_current_assignments` deleted any own-tenant version's reality rows.
The reviewer called it as plain `app_runtime`, in an ordinary unit of work with **no
publication in flight**, against an arbitrary version id: 1 row deleted, V-15c drift
0 → 1, unrecoverable — which disarms D-1b within the tenant, so a later publication can
double-book against emptied reality. The migration's own claim that the runtime gained
"retire the outgoing version's reality rows, not delete from this table" was **false**.

**Fixed** by binding the prune to the publication path through the version's own state.
Publication clears `is_current` at step 08 and marks the prior version `superseded` at
step 11, **both before** the step-12 prune, so two conditions refuse every attack while
leaving the legitimate call untouched:

| Condition | Refuses |
|---|---|
| `is_current` must be false | the reviewer's exact probe — the period's CURRENT version, whose rows *are* the live reality D-1b defends |
| state ∈ {`published`, `superseded`} | pruning against a draft/approved version, which owns no reality at all |

| Test | Result |
|---|---|
| `RED: the reviewer probe — app_runtime pruning a CURRENT version — is REFUSED` | **PASS** — `SCHEDULE_PRUNE_VERSION_IS_CURRENT`, 0 rows deleted |
| `RED: pruning a DRAFT version is refused too` | **PASS** — `SCHEDULE_PRUNE_VERSION_NOT_PUBLISHED` |
| `CONTROL: the legitimate publication path still prunes the outgoing version` | **PASS** — outgoing pruned, incoming inserted |

The two false comments (migration 0009's prune header and the drift test's) now say what
is true and **name the test that holds it true** rather than asserting it.

### B-2 — D-15a did not cover INSERT, and three mutators reached published versions

A `BEFORE UPDATE OR DELETE`-only guard let a published version's child **set grow**: the
reviewer inserted a snapshot against a published `version_id` and the content set went
1 → 2 while every existing row stayed "immutable". I-18 says every child row is
immutable — that is **set**-immutability. Separately, `moveCredit` and `recordConflict`
accepted published versions (a credit then permanently frozen; a conflict unresolvable),
and `recordConflict` had **no capability check and no audit event at all** — an
unconditional violation of non-bypass rules 4 and 6, and the one schedule mutation with
no authorization and no audit trail.

**Fixed** per FAD-22(1): the four child guards are `BEFORE INSERT OR UPDATE OR DELETE`
and check **both sides** of an UPDATE (moving a row *into* a published version is the
same attack). `moveCredit`, `voidCredit` and `recordConflict` gained `assertEditable` —
only 4 of 7 mutators had it — and `recordConflict` gained its capability evaluation and
its `schedule.conflict.recorded` audit event.

| Test | Result |
|---|---|
| `RED: a raw INSERT of a snapshot under a PUBLISHED version raises` | **PASS** — `SCHEDULE_PUBLISHED_IMMUTABLE`; content set stayed 1 |
| `RED: a raw INSERT of a credit against a PUBLISHED version raises` | **PASS** |
| `every one of the 7 content mutators refuses a published version` | **PASS** — all seven |
| `recordConflict evaluates a capability and emits an audit event` | **PASS** — denied for a member; 1 audit row for the authorized call |
| V-06 gained its INSERT arm | **PASS** — UPDATE *and* INSERT refused; content set unchanged |

## 9. Scope discipline

- **No UI.** `apps/web/**` is untouched; the axe gate stays green.
- **No solver, no build pipeline.** `solver/**` is untouched. Manual assignment is
  implemented as override / recovery / fixed-assignment input and is nowhere described or
  positioned as the production scheduling mechanism (non-bypass rule 7). `is_pinned` and
  `origin` exist so the M4 engine can later consume manual content as *fixed input*.
- **No `assignment_audit` table** (CAR-020).
- **Synthetic data only**, far-future 2027+ dates, every address at `example.invalid`.
- **No existing test, gate, invariant or control was weakened.** Where an existing test
  failed (R-05, X-11, the non-vacuity probes), the schema or the fixture was fixed — never
  the assertion.
