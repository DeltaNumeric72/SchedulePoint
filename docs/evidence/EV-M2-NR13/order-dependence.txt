  Diagnosed by reading each one, not inferred from the message:

    1. crash-restart.test.ts:394-400 — this `it` asserts over
       `outbox_events where idempotency_key = 'crash-lease-key'`, a row the
       PRECEDING `it` in the same describe block publishes and dispatches. Run
       first, the row does not exist and `rows[0]?.state` is `undefined`.

    2. outbox-dispatch.test.ts:320-331 — this `it` UPDATEs
       `outbox_events ... where idempotency_key = 'outbox-i11-key'` and expects
       the column CHECK to raise 23514. That row is created by the preceding
       `it`. Run first, the UPDATE matches ZERO rows and therefore SUCCEEDS, so
       the `.rejects` assertion fails. Note the asymmetry, which is worth
       recording on its own: with no row present this assertion cannot fail for
       the right reason — a control test whose subject a sibling test creates is
       one ordering away from being vacuous rather than merely red.

    3. periodic.test.ts:147-158 — "a second sweep writes nothing" depends on the
       preceding `it` having performed the FIRST sweep, which checkpoints the
       head. Run first, the head is uncheckpointed, the sweep legitimately
       writes one, and the expected `[]` is `[{...}]`.

  All three are the same species: a test that did not own its state, reading a
  state a sibling test established. None is a defect in the system under test.
  That is exactly NR-13, and it is INSIDE files — which is why the between-file
  shuffle in section 2 does not surface it.
